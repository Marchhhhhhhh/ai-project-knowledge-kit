# P0 内部自相矛盾（会直接误导执行者）

## R1 记录命名规则与示例互相打架 `[需原项目背景]`

- **位置**：`AGENTS.knowledge.md:39` ↔ `README.md:142`、`:176`、`:191`、`:197`
- **证据**：规则为 "The recommended filename is `YYYYMMDD_sequence-topic.md`; when a corresponding draft exists, its name should make that relationship recognizable"。但示例中同一个草稿 `Drafts/20261117_01.md` 产出的两条记录分别是 `20261117_01-json-export.md`（沿用草稿日期与序号）与 `20261118_01-daily-digest.md`（**另起日期与序号，与草稿名无字面关系**），后者索引 Updated 又写 `2026-11-19`。
- **影响**：新读者无法判断文件名中的 `YYYYMMDD` 是草稿创建日、确认日还是归档日；`_01` 是按天计数还是按草稿计数。两种可能解释各自被一条示例否定。
- **建议**：先向原始项目确认当年实际惯例，再**只选一种**，并同时修改规则句与两条示例：
  - 若采用"跟随草稿"：话题 2 改为 `20261117_02-notification-timing.md`。
  - 若采用"当次日期 + 当日序号"：话题 1 改为 `20261118_01-json-export.md`，并在规则中补一句"日期取确认/归档当天，序号为该日第 N 条记录，Source 列负责建立与草稿的关联"。
- **验收**：仓库内不再出现"规则说 A、示例演示 B"；README 示例中同一草稿的两条记录按同一规则命名。

## R2 索引只能增不能减（缺 rejected / deferred 与退出机制）`[需原项目背景]`

- **位置**：`AGENTS.knowledge.md:63`（状态词表）、`:27` + `:59` + `:62`（待处理行规则）、`:17-18`（每次讨论开场必查），`Progress/Progress.md:4-6`，`Progress/TEMPLATE.md:5`
- **证据**：状态词仅 `pending discussion` / `confirmed, pending implementation` / `implemented` / `amended by a later decision`。关闭一个待处理行的唯一路径是"产出确认结论并归档"；同时 `:74-79` 要求"不要把流程变成噪音"。
- **影响**：讨论后决定"不做"或"无限期搁置"的话题会永久停留在 `Pending discussion`；叠加"每次讨论开场都检查并提醒用户"，索引将退化为每次会议都要过一遍的负债清单，与本 kit 自身的降噪立意冲突。
- **建议**：先确认原项目当时是否已有做法；若无，至少二选一并同步写进协议、索引表头、`TEMPLATE.md:5` 三处：
  - **方案 A**：新增 `Rejected (frozen)` / `Deferred` 状态，规定"否决也是一种确认结论，必须归档并写明否决理由"，待处理行改为指向该记录。
  - **方案 B**：新增"草稿作废（abandoned）"规则，明确谁可标记、标记后是删除行还是保留为 `Abandoned`。
- **验收**：给定"讨论后决定不做"这一场景，新读者能在文档中找到唯一指定的去处与状态值。
